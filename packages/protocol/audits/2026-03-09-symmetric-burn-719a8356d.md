## Key Structural Insight

`totalPredictorTokensMinted` and `totalCounterpartyTokensMinted` are **always equal** in the current system. Every `mint()` adds `totalCollateral` (= predictorCollateral + counterpartyCollateral) to both sides. Every symmetric burn subtracts equal amounts from both. The cross-multiplication check `pA * totalCP != cA * totalP` therefore simplifies to `pA != cA` in all reachable states. The cross-multiply form is more general (future-proof for asymmetric minting) but the team should be aware this is effectively an equality check today.

## Findings

### NEM-001: Orphaned Collateral When Burn Payouts < Backing

**Severity:** MEDIUM  
**Discovery Path:** State Inconsistency (Pass 2)  
**Location:** `PredictionMarketEscrow.sol` — `_executeBurn()`  
**Coupled Pair:** `totalPredictorCollateral + totalCounterpartyCollateral` ↔ actual collateral balance

**Root Cause:** `_executeBurn()` decrements collateral tracking by the full proportional backing, but only transfers the agreed payout amounts (which can be less than backing). The difference stays in the contract but is removed from tracking.

**Trigger Sequence:**
1. Mint: 300 collateral deposited. State tracks `totalCollateral = 300`.
2. Burn 150 tokens each side. Proportional backing = 150. Parties agree payout = 140.
3. State: `totalCollateral` tracked = 150 (reduced by backing of 150).
4. Actual balance: 160 (reduced by payout of 140).
5. Orphaned: 10 collateral, untracked. `sweepDust()` cannot see it.

**Impact:** Collateral permanently stuck in contract. Grows with each under-payout burn. Not exploitable for theft — it's value lost to the void.

**Fix:** Track the surplus explicitly so `sweepDust()` can recover it:
```solidity
uint256 surplus = (predictorCollateralReturned + counterpartyCollateralReturned)
    - (request.predictorPayout + request.counterpartyPayout);
// Add surplus to a dedicated surplus tracker or claimedCollateral
```

**Note:** This is a pre-existing issue, not introduced by PR #1247. The symmetric burn check doesn't affect this path.

### NEM-002: `getSymmetricBurnAmount()` Rounding Inconsistency (Latent)

**Severity:** MEDIUM  
**Discovery Path:** Cross-feed (Feynman Pass 1 → Diff Pass)  
**Location:** `PredictionMarketEscrow.sol:698-722`

**Root Cause:** `getSymmetricBurnAmount()` uses integer division while the burn check uses exact cross-multiplication. If token supplies ever diverge (contract upgrade, future change), the helper returns values that fail the burn check.

**Example (hypothetical unequal supplies):**
- `totalPredictor = 3`, `totalCounterparty = 7`, `tokenAmount = 1`
- Helper returns: `(1 × 7) / 3 = 2`
- Burn check: `1 × 7 = 7 ≠ 2 × 3 = 6` → **reverts with `AsymmetricBurn`**

**Impact:** No current impact (supplies are always equal, so division is exact). Future upgrade risk — a UX helper that lies to users.

**Fix:** Add defensive round-trip check inside the view function:
```solidity
// Verify exactness
require(counterpartAmount * totalSame == tokenAmount * totalOther, "inexact");
```
Or document the invariant dependency: `// NOTE: Exact only when totalPredictorTokensMinted == totalCounterpartyTokensMinted`.

### NEM-003: No Kill Switch on Old Escrow After Upgrade

**Severity:** LOW  
**Discovery Path:** Diff Review  
**Location:** `deploy-all.sh:537-656`

**Root Cause:** The upgrade path deploys new contracts and updates configs. Old contracts remain active (correct for existing positions to settle/redeem), but there's no mechanism to prevent new market creation on the old (vulnerable) escrow if any off-chain system still references the old address.

**Impact:** If API/frontend configs aren't atomically updated, new markets could be created on the vulnerable escrow.

**Fix:** Ensure all off-chain configs are atomically updated. Consider adding a `pause()` function to the escrow for mint-only pausing, or add `onlyOwner` disable for `mint()`.

### NEM-004: Redundant Storage Load in Symmetric Check

**Severity:** LOW  
**Discovery Path:** Feynman (Pass 1)  
**Location:** `PredictionMarketEscrow.sol:403-412` and `418-431`

**Root Cause:** The symmetric check block and conservation check block each create separate storage pointers to `_pickConfigurations[request.pickConfigId]`. While the EVM caches warm SLOADs, the compiler can't reuse the pointer across scoping blocks.

**Impact:** ~200 gas per burn. No security impact.

**Fix:** Merge both checks into a single scoping block:
```solidity
{
    IV2Types.PickConfiguration storage _config = _pickConfigurations[request.pickConfigId];
    // symmetric check
    if (request.predictorTokenAmount * _config.totalCounterpartyTokensMinted
        != request.counterpartyTokenAmount * _config.totalPredictorTokensMinted) {
        revert AsymmetricBurn();
    }
    // conservation check
    uint256 predictorCollateralBacking = ...
    // ...
}
```

### NEM-005: Deploy Script Missing Zero-Address Validation

**Severity:** LOW  
**Discovery Path:** Diff Review  
**Location:** `DeployOnboardingSponsor.s.sol:23-27`

**Root Cause:** Deploy script reads `escrow`, `collateralToken`, `requiredCounterparty` from env vars without checking for `address(0)`.

**Impact:** If env vars are missing or malformed, constructor receives zero addresses. Deployment proceeds but contract is non-functional.

**Fix:** Add `require(escrow != address(0))` before constructor call.

## Methodology

Three parallel audit agents with distinct methodologies:

1. **Feynman Auditor** — First-principles questioning of every changed line. 11 targeted questions covering overflow, ratio preservation, TOCTOU, flash loans, vault interaction, gas griefing, and test coverage.

2. **State Inconsistency Auditor** — Mapped 7 coupled state pairs, traced every mutation path for all `PickConfiguration` fields, cross-checked burn/mint/redeem/settle/sweep paths for desync.

3. **Differential Reviewer** — Analyzed attack surface delta: fix completeness, new view function risk, deploy script safety, SDK address updates, edge cases at boundaries, and test coverage gaps.

Cross-feed phase: Feynman's rounding concern (F-2) + Diff's edge case finding (D-2) → consolidated as NEM-002. State's orphaned collateral finding (S-2) + sweep dust analysis (S-5) → consolidated as NEM-001.

## Conclusion

PR #1247 is **safe to deploy**. The symmetric burn check correctly prevents the asymmetric burn attack. The two medium findings (NEM-001: orphaned collateral, NEM-002: latent rounding) are non-critical — NEM-001 is pre-existing and NEM-002 only activates if the equal-supply invariant is broken in a future upgrade. The recommended test additions would strengthen confidence but are not blockers for deployment.
