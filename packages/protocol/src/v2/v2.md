# PredictionMarket protocol V2 Spec

## Terms
- Condition: Question to be responded (will x team win?)
- Condition resolver: contract that is the source of truth for the resolution of ONE condition.
- Prediction / parlay: collection of one or more picks.
- Meta resolver (prediction resolver): contract that resolves a prediction/parlay by querying the per-pick condition resolvers and applying parlay logic.
- conditionId: opaque bytes32 identifier, resolver-defined (the protocol is agnostic to how it’s derived).
- Pick: (conditionResolver, conditionId, predictedOutcomeSide)
- Outcome vector: resolution output of the form \[yesWeight, noWeight\] (see Condition resolution below).
- Predictor: player that creates the prediction (long / “for” side)
- PredictorWager: amount paid by the predictor on that prediction
- Counterparty: player that takes the other side of the prediction (short / “against” side)
- CounterpartyWager: amount paid by the counterparty

## Requirements and specs

### Main changes in V2 (vs current V1-style boolean resolver + NFT position)
- Each pick can have its own condition resolver, and a separate meta resolver resolves the overall prediction/parlay.
- Resolvers return an outcome vector \[yesWeight, noWeight\] instead of a boolean.
- Positions are represented by a pair of ERC20s (predictor token + counterparty token) per prediction, to enable partial transfers and secondary markets.

### Condition resolution
- Condition resolution is done by a condition resolver contract.
- Resolution uses a vector of two integer values: \[yesWeight, noWeight\]
- Interpretation: \(P(YES) = yesWeight / (yesWeight + noWeight)\) and \(P(NO) = noWeight / (yesWeight + noWeight)\)
- Usual case is decisive YES/NO. Non-decisive vectors (e.g. ties) are supported even if not expected from initial resolvers.
- Examples: 
  - condition resolved to YES, resulting vector is [1,0]
  - condition resolved to NO, resulting vector is [0,1]
  - unresolved for yes/no, resulting vector shows a distribution or balance of yes/no, i.e. tie in a match, resulting vector is [1,1]. Not used at this time (future proof feature).

### Pick encoding (high level)
- The protocol should treat `conditionId` as an opaque `bytes32` value whose meaning and encoding/decoding is defined by the `conditionResolver`.
- Collision resistance:
  - `conditionId` only needs to be unique within a resolver; the pair (resolverAddress, conditionId) forms a namespace.
  - Given that picks are always associated with a resolver address, there is no practical collision risk across different resolvers.
- Recommended pick fields:
  - `conditionResolver` (address)
  - `conditionId` (bytes32)
  - `predictedOutcomeSide` (enum: YES / NO / TIE (optional))
- Canonicalization recommendation (so the “same prediction” hashes/serializes identically):
  - Disallow duplicate picks (same resolver + conditionId repeated).
  - Either require picks to be provided in a canonical order (e.g. sort by (resolver, conditionId, predictedOutcomeSide)), or have the meta resolver enforce canonical ordering before hashing.
  - Use an unambiguous encoding for the list of picks (e.g. ABI-encoding an array of structs) rather than concatenating variable-length blobs.

### Prediction resolution
- Prediction resolution is performed by the meta resolver.
- A prediction can resolve in favor of predictor, counterparty, or become non-decisive (future proof).
- Decisive parlay semantics (current intended behavior):
  - If ALL picks resolve decisively and match the predicted outcomes, the winner is the predictor
  - If ANY pick resolves decisively against the predicted outcomes, the winner is the counterparty
- Non-decisive semantics (future proof):
  - If ALL picks are resolved, but ANY pick is not decisive (i.e. not a pure \[1,0] or \[0,1]), the prediction becomes non-decisive (tie / weighted outcome).
- Payout:
  - Decisive: winner takes PredictorWager + CounterpartyWager
  - Non-decisive (tie): each party receives their original wager (predictor receives PredictorWager, counterparty receives CounterpartyWager)

### Resolver
- Condition resolver: external contract that resolves a single condition to an outcome vector.
- Meta resolver: resolves a prediction by checking each pick against its condition resolver and applying parlay semantics.
- As mentioned in picks definition, a single prediction can contain different condition resolvers, one per pick.

### Integration
- The system will factor and mint a pair of Permissionless ERC20 for each prediction, one for and one against. (predictor and counterparty)
- There's a generic bridge that will be used to bridge the ERC20s to arbitrum to use Cowswap secondary market.
- TBD: Use same address on the ERC20s on each side of the bridge (CREATE2 or CREATE3), or add a map showing the matching tokens on each side of the bridge.

### Collateral
- Both wagers are deposited in ethereal as collateral.
- Collateral is WUSDe. 
- Note: If we want to use native USDe, we should include some kind of escrow of counterpartyWager due to the async mint process

### Mint 
- Mint should accept session key signed.

### Mint process
- Mint function receives a prediction, two addresses, two wager amounts, two sets of signatures, two sets of nonces and deadlines 
- It validates the signatures (crypto signature or sessionKey) -> abstract it
- It validates nonces
- It validates deadlines
- It transfer the collateral from both addresses to escrow. `PredictionCollateral = PredictorWager + CounterpartyWager`
- It creates conditional position tokens for both parties:
  - Factory creates ERC20 predictorToken and counterpartyToken for this prediction
  - Mint supply is fixed at 1 UNIT to each side (1e18 base units) upon prediction creation
  - Tokens are fungible and transferable, enabling partial position sales (e.g. sell 20% of the predictorToken)

### Resolve / settle process (formerly “burn process”)
- Validates the prediction can be resolved via the meta resolver
- Resolves the prediction
- Assigns collateral value to tokens:
  - Decisive: all collateral becomes claimable by the winner token; loser token becomes claimable for 0
  - Non-decisive (tie): predictorToken claimable = PredictorWager, counterpartyToken claimable = CounterpartyWager (future proof)
- Notice: after settlement, the token economics are: 1 UNIT corresponds to the full claim for that side, and partial holders can claim proportionally.

### Collect winnings
- Collection happens on Ethereal network
- The holder of winner token burns the amount of token and receives the proportional part of the winner collateral

### Lifecycle (high level)
- Create prediction:
  - Collect collateral from both parties into escrow
  - Create the two ERC20 position tokens and mint 1 UNIT of each
- Secondary market (optional but enabled by ERC20):
  - Token holders can transfer/sell portions of their position tokens
- Settle prediction:
  - Meta resolver determines outcome (decisive vs non-decisive)
  - Escrow records how much collateral each token is entitled to redeem
- Redeem:
  - Any holder can burn any amount of their position token(s) to redeem proportional collateral

### Invariants / assumptions (high level)
- Escrow must be fully collateralized: total redeemable value across both tokens equals PredictorWager + CounterpartyWager (except any explicit fees, if introduced).
- Resolution must be deterministic for a given prediction definition (same picks + same resolvers ⇒ same result).
- Non-decisive outcomes are future-proof; initial deployment is expected to mostly use pure \[1,0] and \[0,1].

### PredictionMarket
- Holds all the predictions. Manages mint and burn

### Resolver (Condition resolver)
- Condition resolver. Is the source of truth of a condition resolution. It shows if the condition was resolved as YES/NO or is a tie.

### Meta resolver (Prediction resolver)
- Resolves a prediction, checking each pick against the correspoding `resolver` 

### Collateral Escrow and distributor
- Holds the wager collateral of both parties in escrow
- Distributes the collateral to the winner token

### Token factory
- ERC20 factory that creates the predictor and counterparty ERC20 tokens
- It can be a token factory on each network to create the tokens on both sides of the bridge

### Bridge
Bridges position tokens between Ethereal and Arbitrum using LayerZero with two-phase commit (ACK) for safety.

#### Design Principles
- **Permissionless**: No admin functions except LayerZero configuration
- **Automatic**: Token deployment on Arbitrum is automatic on first bridge
- **Safe**: Two-phase commit with ACK confirmation and expiration-based recovery
- **Ethereal-centric**: All administration originates from Ethereal

#### Token Address Determinism
- Uses CREATE3 for deterministic token addresses across chains
- Token address depends only on factory address + salt (predictionId, isPredictorToken)
- Same factory address on both chains ensures same token addresses

#### Token Metadata
- Bridge reads token properties directly from PositionToken contract:
  - `predictionId()`, `isPredictorToken()`, `name()`, `symbol()`
- No pre-registration required - fully permissionless

#### Bridge Flow: Ethereal → Arbitrum

```
1. User calls bridge(token, recipient, amount) on Ethereal:
   - Tokens transferred to bridge (escrow)
   - PendingBridge record created with unique bridgeId and expiry
   - LZ message sent to Arbitrum
   - Status: PENDING

2. Arbitrum receives bridge request (_lzReceive):
   - Deploy BridgedPositionToken via CREATE3 if first time
   - Mint tokens to recipient
   - Send ACK message back to Ethereal
   - Emit TokensMinted event

3. Ethereal receives ACK (_lzReceive):
   - Mark bridge as COMPLETED
   - Emit BridgeCompleted event

4. If no ACK received and expiry passed:
   - User calls cancelBridge(bridgeId) on Ethereal
   - Escrowed tokens returned to original sender
   - Cancel notification sent to Arbitrum (burn if minted)
   - Status: CANCELLED
```

#### Bridge Flow: Arbitrum → Ethereal

```
1. User calls bridgeBack(token, recipient, amount) on Arbitrum:
   - Tokens transferred to bridge (escrow, NOT burned yet)
   - PendingBridge record created with unique bridgeId and expiry
   - LZ message sent to Ethereal
   - Status: PENDING

2. Ethereal receives bridgeBack request (_lzReceive):
   - Release tokens from escrow to recipient
   - Send ACK message back to Arbitrum
   - Emit TokensReleased event

3. Arbitrum receives ACK (_lzReceive):
   - Burn escrowed tokens
   - Mark bridge as COMPLETED
   - Emit BridgeCompleted event

4. If no ACK received and expiry passed:
   - User calls cancelBridgeBack(bridgeId) on Arbitrum
   - Escrowed tokens returned to original sender
   - Cancel notification sent to Ethereal
   - Status: CANCELLED
```

#### Bridge States
- `PENDING`: Bridge initiated, waiting for ACK
- `COMPLETED`: ACK received, bridge successful
- `CANCELLED`: Expired without ACK, tokens returned

#### Expiration Time
- Default: 1 hour (configurable at deploy time)
- After expiry, user can cancel and recover tokens

#### Message Types (LZ Commands)
- `CMD_BRIDGE_TO_REMOTE (1)`: Bridge tokens Ethereal → Arbitrum
- `CMD_BRIDGE_BACK (2)`: Bridge tokens Arbitrum → Ethereal
- `CMD_ACK (3)`: Acknowledge successful bridge
- `CMD_CANCEL (4)`: Cancel notification after expiry

#### Contracts
- `PositionTokenBridge.sol`: Ethereal side - escrow, send, receive ACK
- `PositionTokenBridgeRemote.sol`: Arbitrum side - deploy, mint, burn, receive ACK
- `PositionTokenFactory.sol`: CREATE3 factory for deterministic addresses
- `BridgedPositionToken.sol`: Mintable/burnable ERC20 on Arbitrum

#### Ownership Renouncement

For maximum decentralization, all bridge contracts support safe ownership renouncement after configuration is complete.

##### Helper Functions

Each contract provides:
- `isConfigComplete()` - Returns true if all required configuration is set
- `renounceOwnershipSafe()` - Reverts if config incomplete, otherwise renounces ownership

##### Configuration Requirements

| Contract | Required Config |
|----------|----------------|
| PositionTokenBridge | remoteEid, remoteBridge, LZ peer |
| PositionTokenBridgeRemote | remoteEid, remoteBridge, LZ peer |
| PositionTokenFactory | deployer address |

##### Renouncement Sequence

1. Complete all LZ configuration (setBridgeConfig, setPeer)
2. Test cross-chain messaging in production
3. Verify: `isConfigComplete()` returns true on all contracts
4. Renounce factory first, then both bridges

##### Post-Renouncement State

After renouncing:
- Bridge configuration is permanent
- No new chains can be added
- Contracts become fully trustless
- Any upgrades require new deployment
